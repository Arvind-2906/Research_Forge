# ResearchForge Database Schema & Storage Architecture

**Database Engine:** Neon Serverless PostgreSQL  
**Extensions:** `pgvector`  
**Migration Owner:** Node.js Backend (`backend/node-server/prisma`)  
**ORM / Data Access:** Prisma ORM (Node.js) & `asyncpg` Connection Pool (Python AI Engine)  

---

## 1. Overview & Data Ownership

ResearchForge uses **Neon PostgreSQL** as its single, persistent source of truth. All domain entities, multi-agent checkpoints, research evidence, semantic memory embeddings, and knowledge graph structures are stored within this database.

### Core Principles
1. **Node.js Owns Migrations**: All schema modifications, Prisma migrations, and pgvector extension setups must be executed through the Node.js backend using `npx prisma migrate dev` or `npx prisma migrate deploy`.
2. **Python AI Engine is a Consumer**: The Python AI Engine never executes DDL migrations. It connects via `asyncpg` connection pools to execute high-performance relational queries and vector similarity searches.
3. **Multi-Tenant Workspace Scoping**: All core domain tables (Projects, Runs, Memories, Sources, Knowledge Nodes) require foreign key association to `Workspace` to ensure strict tenant isolation.

---

## 2. PostgreSQL Extensions

### `pgvector`
The `vector` extension is enabled at the root database level.
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

Vector columns are configured for **384-dimensional embeddings** generated by `BAAI/bge-small-en-v1.5`:
- `ResearchMemory.embedding`: `Unsupported("vector(384)")?`
- `SourceChunk.embedding`: `Unsupported("vector(384)")?`
- `DocumentAsset.embedding`: `Unsupported("vector(384)")?`
- `KnowledgeNode.embedding`: `Unsupported("vector(384)")?`

Vector similarity is evaluated using **Cosine Distance** (`<=>` operator):
$$\text{Cosine Similarity} = 1 - (\vec{u} \cdot \vec{v})$$

## 3. Database Domain Models

The database contains 35 relational models grouped into 9 functional domains.

### 3.1. Authentication & User Identity (Better Auth)
- **`User`**: Core user record storing identity, email, name, image, role, and timestamps.
- **`Session`**: Active user sessions referencing `User`, holding token and expiration dates.
- **`Account`**: OAuth accounts (Google, GitHub) linked to users with provider credentials.
- **`Verification`**: Time-limited verification tokens for email verification or password resets.

### 3.2. Workspaces & Access Control (RBAC)
- **`Workspace`**: Root tenant container. Owns projects, memories, sources, and knowledge nodes.
- **`WorkspaceMember`**: Junction table mapping users to workspaces with role-based access:
  - `OWNER`: Full administrative privileges, billing, workspace deletion.
  - `ADMIN`: Member management, project creation, settings.
  - `MEMBER`: Project creation, research execution, report generation.

### 3.3. Projects & Research Runs
- **`ResearchProject`**: Categorical workspace folder grouping related research runs.
- **`ResearchRun`**: Represents a single research lifecycle execution.
  - **Statuses (`ResearchRunStatus`)**: `QUEUED`, `PLANNING`, `RUNNING`, `VERIFYING`, `SYNTHESIZING`, `WAITING_FOR_APPROVAL`, `PAUSED`, `REQUIRES_INPUT`, `COMPLETED`, `FAILED`, `CANCELLED`.
  - Tracks research query, depth, breadth, timestamps, failure reasons, and duration.

### 3.4. Research Planning & Multi-Agent Execution
- **`ResearchPlan`**: High-level execution roadmap generated by the Planner Agent.
  - **Statuses (`PlanStatus`)**: `DRAFT`, `APPROVED`, `REJECTED`, `SUPERSEDED`.
- **`ResearchTask`**: Sub-tasks broken down by the planner, assigned to specific agent types.
- **`ResearchTaskDependency`**: Directed acyclic graph (DAG) dependencies between research tasks.
- **`AgentExecution`**: Records individual agent execution instances, inputs, outputs, and tokens.
- **`ResearchEvent`**: Monotonically ordered audit trail and streaming event bus for runs:
  - Fields: `runId`, `sequence` (Int), `type`, `agent`, `severity`, `title`, `message`, `payload`, `timestamp`.
  - Protected by unique index `@@unique([runId, sequence])`.

### 3.5. Sources & Content Extraction
- **`ResearchSource`**: Web URLs, academic DOIs, or GitHub repositories discovered by agents.
  - **Types (`SourceType`)**: `WEB`, `ACADEMIC`, `REPOSITORY`, `DOCUMENT`, `API`, `OTHER`.
  - **Statuses (`SourceStatus`)**: `DISCOVERED`, `EXTRACTED`, `FAILED`, `ARCHIVED`.
- **`SourceSnapshot`**: Immutable archival snapshot of extracted raw text, markdown, or HTML.
- **`ResearchRunSource`**: Many-to-many relationship tracking which sources were used in which run.
- **`SourceChunk`**: Text passages with 384-dimensional vector embeddings for RAG retrieval.

### 3.6. Verification & Evidence
- **`ResearchClaim`**: Empirical assertions extracted from findings that require fact-checking.
  - **Statuses (`VerificationStatus`)**: `PENDING`, `VERIFIED`, `PARTIALLY_VERIFIED`, `CONTRADICTED`, `REJECTED`.
- **`Evidence`**: Specific quoted excerpts supporting or contradicting a claim with confidence score.
- **`ClaimEvidence`**: Many-to-many mapping connecting claims to evidence with relationship (`SUPPORTS`, `CONTRADICTS`, `CONTEXTUALIZES`).

### 3.7. Reports & Document Exports
- **`ResearchReport`**: Final synthesized research paper with abstract, sections, methodology, and conclusion.
- **`ReportCitation`**: Academic-grade citation records linked to verified sources.
- **`ReportExport`**: Compiled binary exports (`PDF`, `DOCX`, `MARKDOWN`, `HTML`) with storage file paths.

### 3.8. Scoped Memory & Document Assets
- **`ResearchMemory`**: Vector-indexed memory units with 3 scopes:
  - `USER`: User preferences and habits.
  - `WORKSPACE`: Shared workspace research guidelines and domain taxonomy.
  - `PROJECT`: Contextual facts specific to a research project.
- **`DocumentAsset`**: User-uploaded files (PDF, TXT, DOCX) indexed for hybrid RAG search.

### 3.9. Remote MCP & Tool Telemetry
- **`MCPServer`**: Remote MCP endpoint registration (Tavily, Exa, Firecrawl, GitHub).
- **`MCPTool`**: Discovered tool schemas, parameters, and permission levels.
- **`MCPToolCall`**: Complete invocation telemetry: arguments, output, status (`SUCCESS`, `FAILED`), duration in milliseconds.
- **`MCPToolPermission`**: Workspace-level allow/deny policies for tool execution.
- **`MCPApprovalRequest`**: Human-in-the-loop permission requests for high-risk tools.
- **`ExternalConnection`**: OAuth credentials and API tokens for external providers.
- **`LLMInvocation`**: Token usage telemetry: prompt tokens, completion tokens, model, provider, latency.

### 3.10. Knowledge Graph
- **`KnowledgeNode`**: Graph entity (Topic, Concept, Claim, Person, Organization, Technology) with vector embeddings for semantic graph traversal.
- **`KnowledgeEdge`**: Directed relationship connecting knowledge nodes (`RELATED_TO`, `SUPPORTS`, `CONTRADICTS`, `DEPENDS_ON`, `PART_OF`, `COMPARES_WITH`, `REFERENCES`) with strength weight (0.0 - 1.0).

## 4. Concurrency & Monotonic Sequence Guarantees

To ensure Server-Sent Events (SSE) provide a strictly monotonic event stream without race conditions across concurrent agent workers:

```sql
-- Executed inside an explicit transaction in the AI Engine
BEGIN;

-- Lock parent ResearchRun row to serialize sequence generation
SELECT id FROM "ResearchRun" WHERE id = $1 FOR UPDATE;

-- Generate next sequential number
INSERT INTO "ResearchEvent" ("id", "runId", "sequence", "type", "title", "message", "timestamp")
VALUES ($2, $1, (SELECT COALESCE(MAX("sequence"), 0) + 1 FROM "ResearchEvent" WHERE "runId" = $1), $3, $4, $5, NOW())
RETURNING "sequence";

COMMIT;
```

## 5. Prisma Migration Workflow

1. **Modify Schema**: Edit `backend/node-server/prisma/schema.prisma`.
2. **Generate Migration**:
   ```bash
   cd backend/node-server
   npx prisma migrate dev --name <migration_name>
   ```
3. **Deploy Migration in Production**:
   ```bash
   npx prisma migrate deploy
   ```
4. **Regenerate Prisma Client**:
   ```bash
   npx prisma generate
   ```
